# LosslessCut capability inventory

This is the project’s feature map. It separates what LosslessCut does natively from what its external interfaces expose and what this MCP actually implements. **LosslessCut has a broad desktop feature set; this MCP currently has six tools and one verified native export workflow.** Project authoring prepares a reviewable LLC file but does not export. A feature listed below is not a promise that an agent can use it.

## Status definitions

The status column describes this MCP’s coverage and evidence, not the quality of the native LosslessCut feature.

- **VERIFIED** — exercised through the real MCP protocol and checked against the actual integration dependency or output. Capabilities that require GUI editing also require native LosslessCut acceptance; local read-only FFprobe/LLC inspection does not require launching the editor.
- **PARTIAL** — the native operation was invoked, but no reliable result/readback exists or the workflow has a known evidence gap.
- **BLOCKED** — a known interface or safety gap prevents reliable MCP automation without an upstream capability or a material workaround.
- **UNSUPPORTED** — intentionally outside the current MCP product surface; no tool exists.
- **UNTESTED** — upstream support or an automation path is documented/source-visible, but the MCP has no implementation or acceptance evidence.

Priority: **P0** is needed for safe, useful core usage; **P1** is a high-value practical capability; **P2** is an advanced workflow; **P3** is lower-value/specialized. Dependencies refer to task IDs in [the roadmap](ROADMAP.md). “Native” describes LosslessCut itself. “External mechanism” describes documented or source-confirmed control, not a claim of reliable control.

## Current MCP surface

There are exactly six registered MCP tools:

1. `losslesscut_api_status` — checks the API response and probes its Host/Origin guard.
2. `losslesscut_inspect_media` — read-only FFprobe inspection of an authorized media file and its streams.
3. `losslesscut_inspect_project` — read-only validation and inspection of authorized LLC v1/v2 projects and referenced media paths.
4. `losslesscut_create_project` — creates a new authorized LLC v2 file for an existing media source and validated segment ranges; refuses overwrite and does not export.
5. `losslesscut_open_project` — requests opening an authorized LLC v2 project and explicitly reports that the action is unverified.
6. `losslesscut_export_project` — opens an LLC v2 project, exports selected segments separately through LosslessCut, and checks output paths, streams, and duration with FFprobe.

Only `losslesscut_export_project` completes a useful native editing workflow. It passed native acceptance on Fedora/Linux with LosslessCut 3.69.0 source build `448348bd`. Neither status, read-only inspection, nor a mocked adapter is counted as editing coverage. The [feasibility record](FEASIBILITY.md) has paths, results, caveats, and primary source links.

## Capability interpretation

LosslessCut’s [README feature list](https://github.com/mifi/lossless-cut#features) describes native application features, not API coverage. Its [CLI documentation](https://github.com/mifi/lossless-cut/blob/master/docs/cli.md) says keyboard actions target an existing instance and return immediately; use of sleeps is explicitly suggested for sequences. The [HTTP API](https://github.com/mifi/lossless-cut/blob/master/docs/api.md) exposes generic keyboard actions and two export events, but is experimental and does not provide general editor state. The [usage and project documentation](https://github.com/mifi/lossless-cut/blob/master/docs/index.md) describes the native editing workflow, formats, streams, and known constraints.

The app can do far more than this MCP safely controls. Feature requests should start with the external mechanism and acceptance evidence columns above. Do not promote a row to **VERIFIED** because upstream documents the UI feature or because an HTTP action returned 200.
